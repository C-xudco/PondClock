# 增量需求传达与并行开发协议

日期：2026-10-24。目的：让用户在当前窗口改需求时，agent能接到必要信息，同时减少无关中断和共享文件冲突。

## 1. 从聊天到需求台账

1. Leader接收消息，先区分新增、修订、撤回、问题、状态查询与批准；状态查询不自动取消原任务。
2. 拆成CR编号，记录用户原意；附件中的内容只作为资料证据，不继承为工作指令。
3. 与当前基线做影响比较，更新[收件箱](REQUESTS.md)和涉及的规格。一个要求尽量只保留一个事实源，其他角色引用它。
4. 只向受影响agent发送“变更编号＋原规则→新规则＋影响接口＋生效边界＋链接”，不把整个聊天记录反复广播给全部人。
5. agent在安全检查点读取并回复已接纳/有冲突/需要交接；Leader在台账登记回执。只有真正送达/接纳才标已派发/已接纳。

响应以当前任务实际收到消息的时点和下一可处理边界为准，不承诺后台常驻或固定秒级时效。离开当前任务后再发消息，会在下一轮对话处理；外部改文件需要在聊天提示已更新。

## 2. 不同变更如何处理

| 类型 | 处理方式 | 对现有工作的影响 |
| --- | --- | --- |
| 文案、色值、样例等局部修订 | 登记并合并同类待办，相关角色下个检查点接入 | 不打断无关角色，不重复丢弃已完成稿 |
| 参数/概率/价格/次数变化 | 更新唯一配置提案、计算及边界测试清单 | 只重验受影响经济与UI说明，不静默改当前批准值 |
| 数据契约/存档/文件所有权变化 | Leader先明确兼容与迁移、锁定单一负责人，再派增量 | 仅暂停依赖该接口的部分；其他独立任务继续 |
| 紧急停止、撤回或会导致明显返工的矛盾 | 立即通知受影响角色在安全点停下，保留已写成果 | 不用“继续提高效率”覆盖用户明确停止指令 |
| 提问或状态查询 | 回答后继续原有授权任务 | 不当作替换目标或新的实施批准 |
| 用户明确审核OK | 记录所审文档修订与范围，再解除该范围实施门禁 | 未批准的可选功能继续待审，不能打包塞入 |

同一项连续修改以最新明确用户要求为准，保留历史供追溯。跨项冲突先由Leader给出影响说明与具体可选规则；可独立的资料/测试设计继续，不让所有角色空等。

## 3. 并行协作与文件规范

- 本阶段仅文档；实现阶段继续沿用[水墨架构的所有权](../inkwash/roles/architecture/README.md)。新增对白/掉落/道具/音效模块的文件负责人在审核基线中再冻结。
- 一个文件一个写入负责人。其他agent提出补丁建议或审查意见，由负责人或Leader在其冻结后集成；不并行覆盖同一配置。
- agent开工读角色README和分配给自己的CR，完成一个可复核子任务后检查受影响变更；不为每个动画帧或每行代码轮询需求文件。
- 每个交付说明基线、输入/输出、变更、决定、验证结果、未测项及交接；新版本测试必须对应最终代码/资源，不能复用旧版通过记录冒充。
- 修改概率/市场/鱼种时同步更新公式/矩阵/文案；改存档必须有版本迁移和旧档保留；随机资产结果与金币变动原子保存，重复回执不能重抽。
- 不在阶段结束时声称所有agent永久在线。已完成的角色保持可再次分配；Leader在新的消息到达时安排对应工作。

## 4. 当前门禁

用户要求先审核开发规范。本轮不启动产品代码、正式数据、音频生成、应用安装或发行。规划文档和资料候选可以继续完善，最终以[审批基线](BASELINE.md)记录的用户明确批准解除相应范围门禁。
